# Driving the fold build of opencode from a script: lessons (2026-11-10)

Observed with `opencode v2.0.29-fold`, macOS, running one stateless step per `opencode run` (no tools, a one-line system prompt) to test building software from small briefs. Each item says how it was observed; nothing here is from reading the source unless it says so.

1. **`opencode run` waits for its stdin to close when stdin is a pipe.** Symptom: the process stays alive at 0% CPU, writes no session and prints nothing. From Node, spawn with `stdio: ["ignore", "pipe", "pipe"]`; from a shell, redirect `</dev/null`. Measured with one call each way: 2.9 s with stdin ignored, killed at the 25 s limit with an open pipe. A first guess that parallel runs were the problem was wrong; test the cheap alternatives (stdin, title, prompt size, parallelism) one at a time.
2. **Isolate the config, not the data directory.** Setting `XDG_CONFIG_HOME` to a private folder with its own `opencode.json` stops the global config loading: MCP servers, global instructions files and plugins. But provider credentials live in a `credential` table of the data directory's database (each of the `opencode*.db` files has one), so an isolated `XDG_DATA_HOME` has no providers and every model fails with `provider.no-route` / "Model unavailable: <model>", which looks like an account problem and is not. Keep the real data directory (sessions then show up in its history; `--title` makes them findable) and do not copy the database, because it holds credentials.
3. **A wrapper may route `opencode` somewhere else.** In an interactive terminal the plain command here printed a note that it runs on a remote workspace and pointed at a local variant; credentials added through one variant are in that variant's store. Check which binary you are running and where it stores sign-ins before signing in.
4. **A no-tools single-reply agent**: a custom agent with `mode: "primary"`, a one-line `prompt`, `tools: {"*": false}`, and `permission` set to `deny` for bash, edit, read, write and webfetch. Overhead observed: about 490 input tokens per call beyond the prompt (607 input tokens for a 117-token brief).
5. **Read the result with `--format json`.** Lines of type `text` (`part.text`), `step_finish` (`part.tokens` with input, output, reasoning, cache, and `part.cost`) and `error`. Without it an error can be swallowed and the run looks like a hang; `--print-logs --log-level debug` also shows it.
6. **Hidden reasoning dominates time and tokens for the DeepSeek models behind opencode-go.** A 2 K-token source file came with about 4.5 K reasoning tokens and took 54 s ($0.004); a one-digit closed answer took 3.6 to 4.4 s ($0.0002 to $0.0006). Budget wall time for the first.
7. **With no door running, the plugin logs "fold doorway speaks an older contract" and the run carries on** (it fails open). Models configured against door ports fail if the door is down; a local Ollama endpoint worked.
8. **Do not `pkill -f` a pattern like `opencode run`.** The desktop app and other sessions run the same binary. Kill by the PID of the harness you started and its children (`pgrep -P`).
9. **Sessions from scripted runs land in the normal session history.** Give them a recognizable `--title` and delete them after, or use a distinct data directory only if you can give it credentials some other way.
